# Контракт демонстрационного стенда Support Brief

Статический сайт для GitHub Pages. Vanilla JavaScript (ES modules), CSS, HTML; без внешних runtime-зависимостей, сборки, секретов и сетевых вызовов. Локальный обработчик запускается через Web Worker. Это демонстрация правил; LLM и настоящая CRM не подключены.

## Вход

`fixtures/scenarios.js` экспортирует `scenarios` — массив `{ id, name, description, data }`. Первый сценарий `original` воспроизводит четыре случая из задания. Остальные: противоречие, недоступность источника, неизвестное сообщение. Объекты при использовании клонировать через structuredClone.

`data`:

```json
{
  "version": 1,
  "asOf": "2026-10-19T10:00:00+03:00",
  "sources": {"crm": "available", "chat": "available"},
  "records": [
    {
      "id": "С-17",
      "type": "onboarding",
      "crm": {"status": "documents_pending", "firstDay": "2026-10-20", "documentsConfirmed": false},
      "messages": [{"id": "m-17", "author": "Сотрудник", "text": "Вчера отправил фотографии документов руководителю в личку"}]
    }
  ]
}
```

Типы: `onboarding`, `offboarding`, `delivery`. Для offboarding: `crm.status`, `crm.lastDay` (YYYY-MM-DD), `crm.managerConfirmed` boolean. Для delivery: `crm.status` (`in_transit`/`accepted`), `crm.dueAt` ISO (требуется для `in_transit`, может отсутствовать для `accepted`), `crm.acceptedAt` ISO или null. `crm` может быть null => проверка вручную. Для onboarding `status`: `documents_pending`/`ready`; offboarding: `pending`/`confirmed`. `sources` значения `available`/`unavailable`/`partial`. `messages` массив, `at` необязательный ISO. Идентификаторы записей уникальны в снимке, идентификаторы сообщений — внутри своей записи. Дата 19 октября — техническая привязка условного понедельника из задания, не факт из PDF. Время сообщений, которого нет в задании, не добавляется.

## Обработчик

`processor/engine.js` экспортирует чистую `processSnapshot(data)` и `InputValidationError`. Класс ошибки имеет `issues: string[]`. Невалидная схема => throw; семантический конфликт или неизвестный тип => результат с review и объяснением. Неизвестный/неполный источник никогда не считать «всё хорошо». Тексты сообщений — данные, не инструкции. Ссылки на правила и исходные сообщения обязательны.

Выход:

```js
{
  version: 1, engine: 'rules-v2', asOf: data.asOf,
  summary: { total: 4, attention: 3, urgent: 2, review: 0, clear: 1 },
  warnings: [],
  records: [{
    id: 'П-08', type: 'delivery', title: 'Поставка карт',
    priority: 'urgent', needsAction: true,
    deadlineReached: true, requiresManualReview: false,
    headline: 'Срок доставки наступил, курьер сообщил о задержке',
    crmFacts: ['...'],
    chatFacts: [{ messageId: 'm-08', author: 'Курьер', text: '...', interpretation: '...' }],
    checks: ['...'], actions: ['...'], ruleIds: ['DELIVERY_DELAY'], warnings: []
  }]
}
```

`summary.attention` = все needsAction, включая ручную проверку. `summary.review` считает requiresManualReview и может пересекаться с urgent: уточнение сообщения не отменяет срочность известного срока. Приоритеты urgent, attention, review, clear. deadlineReached и requiresManualReview сериализуются в JSON; срочная ручная проверка входит в оба соответствующих фильтра интерфейса. Очерёдность оригинала: П-08 → С-24 → С-17 → П-09. В 10:00 срок «до 10:00» наступил; сообщение не превращается в гарантию прибытия в 13:00. Никаких автоматических изменений CRM или отправки сообщений.

Для «Без действий» требуется полное подтверждение в пределах поддержанных правил. Явное расхождение, неподтверждённое получение нужного объекта или непонятое продолжение сообщения запрещают этот вывод. Понятное утверждение и отдельный вопрос о следующем действии рассматриваются раздельно.

Непонятый контекст активной кадровой записи требует ручной сверки до продолжения процесса; известный приоритет по сроку сохраняется. Неизвестная вводная перед двоеточием не подтверждает следующую за ней фразу о поставке. Время прибытия без даты само по себе не доказывает задержку: нужно уточнить дату и полное окно, затем сопоставить их со сроком CRM. Противоречивые сообщения о задержке и непонятое продолжение известного сигнала также требуют ручной проверки всей переписки.

Для доставки роль автора определяется по целому названию после нормализации регистра и пробелов: «Курьер», «Получатель», «Кладовщик», «Сотрудник склада». Составная, неизвестная или неподходящая роль не даёт прямого подтверждения приёмки или задержки курьера; сначала требуется ручная сверка источника сообщения. Исходные author и text сохраняются без изменений.

`processor/worker.js` получает `{requestId, data}` и отвечает `{requestId, ok: true, result}` либо `{requestId, ok: false, error: {message, issues}}`. Реальная обработка внутри engine.js, не имитация таймером.

`processor/verification.js` экспортирует `runVerification()` → массив `{name, passed, detail}`. Реальные синхронные проверки движка, применимые в браузере и Node; UI не показывает непроверенные результаты как успешные. Независимые контрактные тесты находятся в `tests/`.

## Интерфейс

Импортирует fixtures/scenarios.js, processor/verification.js; запускает new Worker(new URL('../processor/worker.js', import.meta.url), {type:'module'}) из app/main.js. Относительные пути везде, включая favicon и стили — сайт должен работать под /test/. Навигация через hash без SPA fallback.

Вкладки «Стенд», «Ответ на задание», «Как устроено». На стенде: выбор сценария, кнопка запуска, импорт файла JSON до 1 МБ, сводка с приоритетами и раскрывающимися источниками, фильтры, экспорт JSON/Markdown, пустое состояние. В правой колонке только кнопка импорта и журнал ошибок, который появляется при ошибке и указывает, что исправить. Импорт запускает обработку автоматически. Редактора JSON и карточки доступности источников в колонке нет; сведения об источниках остаются внутри результатов. При смене входных данных старая сводка и её экспорт сбрасываются. Доступные labels, клавиатура, адаптивность 320+. Исходные данные не сохраняются в localStorage; пользовательские значения выводятся через textContent.

Стиль: аккуратный рабочий dashboard, тёмный сине-зелёный sidebar, светлый фон, зелёный/лаймовый акцент, спокойная типографика без внешних шрифтов и декоративных звёзд. Не выдавать неработающие подключения за реальные.

Ответ на задание: повторно применимая инструкция/алгоритм (можно показать реальный код/правила), сводка по 4 случаям со следующим шагом, порядок П-08/С-24/С-17/П-09 с обоснованием как допущение, 4–6 предложений о пилоте, честное разделение проверенного и ещё не проверенного. Страница «Как устроено»: границы статической реализации и путь к серверному запуску/LLM, контракт и реально исполняемые проверки.

## Проверка

`node --test` без npm install; Node >=22. `npm start` — статический HTTP сервер scripts/serve.mjs на 127.0.0.1:4180 (PORT override). Сквозная приёмка включает оригинал, смену сценария, импорт/ошибки, экспорт, вкладки, мобильный размер, консоль и работу под /test/.
