# Support Brief

Демонстрационный стенд для тестового задания Руссмаркет: ежедневная сводка support-отдела на основе CRM и рабочих переписок.

## Запуск

Нужен Node.js 22 или новее. Установка пакетов и сборка не требуются.

```powershell
cd E:\gitRepos\test
npm start
```

Открыть http://127.0.0.1:4180/. ES modules и Web Worker требуют HTTP: открытие `index.html` через `file://` не поддерживается.

```powershell
npm test
npm run check
```

`npm test` запускает независимые проверки поведения обработчика; `npm run check` проверяет синтаксис модулей и относительные ссылки HTML. На вкладке «Как устроено» также доступны реальные проверки движка в браузере. Они не заменяют приёмку на реальных данных.

Результаты локальной сквозной проверки: [docs/acceptance.md](docs/acceptance.md). Независимая проверка движка: [docs/qa-review.md](docs/qa-review.md).

## GitHub Pages

1. Загрузить содержимое этой папки в корень своего репозитория.
2. Открыть **Settings → Pages**.
3. Выбрать **Deploy from a branch**, свою ветку (например, `main`), папку **/(root)**, сохранить.
4. Дождаться публикации и открыть выданный GitHub адрес.

Все пути относительные; имя репозитория не зашито. `.nojekyll` позволяет отдавать файлы как статические ресурсы. Вкладки используют hash-навигацию, поэтому отдельный fallback для маршрутов не нужен. Для проверки размещения в подпапке локально:

```powershell
$env:PORT = '4181'
$env:BASE_PATH = '/test'
npm start
```

Открыть http://127.0.0.1:4181/test/. После остановки переменные можно убрать через `Remove-Item Env:PORT,Env:BASE_PATH -ErrorAction SilentlyContinue`.

## Что делает стенд

- Обрабатывает четыре исходных случая и дополнительные сценарии с проблемами качества данных.
- Импортирует JSON-снимок по контракту и автоматически формирует сводку.
- Показывает ошибки импорта и обработки с указанием поля и способа исправления.
- Отделяет сведения CRM от сообщений, показывает основания, проверки и следующие шаги.
- Формирует порядок работы, фильтрует случаи и экспортирует сводку.
- Содержит отдельный ответ на все пункты тестового задания и объяснение устройства.

## Граница демонстрации

GitHub Pages размещает статические файлы. Здесь сервисный модуль реально выполняет обработку в Web Worker внутри браузера. CRM, мессенджеры, LLM и планировщик не подключены. Ключи API не нужны, данные не отправляются на сервер и не сохраняются в localStorage. После перезагрузки введённые данные и локальные отметки теряются; экспорт сохраняется только по действию пользователя.

Скрипт использует ограниченные правила интерпретации сообщений и точные проверки структурированных полей CRM. Он не предназначен для произвольной переписки: неизвестные формулировки требуют ручной проверки. Содержимое сообщений рассматривается как данные, а не как инструкции для системы. Изменения статусов CRM и отправка сообщений не выполняются.

Заключение «Без действий» допускается только при полном подтверждении в рамках поддержанных правил. Непонятное продолжение или расхождение не отбрасываются. Срочность наступившего срока и необходимость ручной проверки учитываются отдельно: одна запись может входить в обе группы.

В исходном задании указано «понедельник, 10:00» без календарной даты. Для воспроизводимых проверок выбран понедельник 19 октября 2026 года, часовой пояс МСК. Время сообщений, которого нет в задании, не добавляется. Дополнительные сценарии — специально созданные тестовые данные.

## Устройство

```text
index.html             Оболочка приложения
app/                   Интерфейс, стили, текст ответа
fixtures/              Исходный и дополнительные сценарии
processor/engine.js    Чистая обработка снимка → сводка
processor/worker.js    Асинхронный адаптер для браузера
processor/verification.js  Исполняемые проверки в браузере и Node
tests/                 Независимые автоматические проверки
scripts/               Локальный HTTP-сервер и проверка синтаксиса
CONTRACT.md            Общий контракт модулей
docs/qa-review.md       Отчёт независимой проверки
```

Движок не зависит от DOM и Web Worker: его можно перенести в серверный обработчик без переписывания бизнес-правил. Worker отвечает за изоляцию вычисления, интерфейс — за состояние запроса и отображение. Ошибки схемы и случаи, требующие ручной проверки, обрабатываются отдельно.

## Первый рабочий пилот

На сервере адаптеры получают снимок CRM и доступные сообщения, сопоставляют их по ID операции и передают нормализованные данные в тот же движок. Планировщик запускает сбор утром; идентификатор снимка защищает от повторной доставки одной сводки. Если потребуется LLM, она извлекает из переписки структурированные утверждения со ссылками на сообщения; сроки, статусы и итоговые решения проверяются правилами. Ключи и доступы хранятся на сервере. Первое время сотрудник сверяет сводку с источниками и самостоятельно выполняет действия; вместе с support измеряются время разбора, пропуски важных случаев и ложные тревоги на размеченной выборке.

Работа с реальной CRM, полнота и задержки загрузки сообщений, полномочия авторов, обработка персональных данных и фактическая экономия времени требуют отдельной проверки. Успешное демо не подтверждает производственную готовность интеграций.
